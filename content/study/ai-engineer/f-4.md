Choosing a model and designing a request is always a **trade-off between quality, cost and speed**. This lesson gives you the numbers to reason about it.

## The context window

The **context window** is the most tokens a model can consider in one request: **input + output together**.

```
┌────────────────────── context window (e.g. 1M tokens) ──────────────────────┐
│ system prompt │ tools │ conversation history │ documents │ ... │ output     │
└──────────────────────────────────────────────────────────────────────────────┘
```

Current Claude models have **1M-token** windows (roughly 750,000 words) and can write up to **128K tokens** of output in one response.

Big windows are useful, but:

- **You pay for every input token on every call.** A chat that resends 200K tokens of history each turn gets expensive fast.
- **More context = slower** time to first token.
- **Quality can drop** when the important part is buried in a huge prompt. Put the right text in, not all the text (RAG module).

## Working out cost

```
cost = input_tokens / 1,000,000 × input price
     + output_tokens / 1,000,000 × output price
```

Example: a support bot on Opus 5.5, 3,000 input + 500 output tokens per reply, 10,000 replies a month:

```
input:  3,000 × 10,000 = 30M tokens × $4  = $120
output:   500 × 10,000 =  5M tokens × $20 = $100
total ≈ $220 / month
```

The same on Haiku 5.5: 30M × $0.10 + 5M × $0.50 = **$5.50**. If Haiku is good enough (measure it with an eval!), that's a 40× saving.

**Thinking tokens count as output.** A model that reasons before answering produces more output tokens.

## Latency

Two numbers matter:

- **Time to first token (TTFT):** how long until anything appears. Driven by input size and model.
- **Output speed:** tokens per second once it starts.

```
total time ≈ TTFT + output_tokens ÷ tokens_per_second
```

So **long outputs are slow**, whatever the model. Ways to make it *feel* fast:

- **Stream** the response so users see words immediately (API module).
- Ask for **shorter answers**.
- Use a **smaller model** or **lower effort** for simple steps.
- Run independent calls **in parallel**.

## Choosing: a simple procedure

1. Start with the **best model** (Opus 5.5) to see what's possible.
2. Build a small **eval** (even 20 examples).
3. Try cheaper models or lower effort; **keep the cheapest that passes**.
4. Different steps can use different models (a Haiku classifier in front of an Opus answerer).

## Check yourself

1. A request sends 900K tokens and asks for 150K of output on a 1M-context model. What happens?
2. Why does a chatbot get more expensive the longer a conversation goes?
3. Your answer takes 20 s to generate. Name two ways to improve the experience.

### Answers

1. Input + output exceed the 1M window (and 150K is above the 128K output cap), so it fails; send less input and lower `max_tokens`.
2. The API is stateless, so each turn resends the whole history; input tokens grow every turn (caching helps).
3. Stream it, ask for a shorter answer, use a faster model or lower effort.
