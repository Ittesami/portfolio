Beyond the six pillars, a few **general design principles** run through all of AWS's advice. When two answers both "work", the one that follows these principles is usually right.

## Design for failure

> "Everything fails, all the time." (Werner Vogels, Amazon's CTO)

- Assume any component can fail and plan for it.
- Avoid **single points of failure**: one server, one database, one AZ.
- Use **multiple Availability Zones**, health checks and automatic recovery.

```
single point of failure:  users → [ one server ] → [ one database ]
designed for failure:     users → load balancer → [ servers in AZ a + AZ b ]
                                                → [ database + standby in another AZ ]
```

## Decouple components

Connect components **loosely** (queues, notifications, APIs) so one failure doesn't cascade: **SQS**, **SNS**, microservices (Module 2).

## Implement elasticity

Scale automatically with demand, up **and** down: **Auto Scaling**, **serverless** (Lambda, Fargate, DynamoDB).

## Think parallel, automate everything

- Do work in **parallel** (many small instances or functions instead of one big one).
- **Automate:** infrastructure as code (CloudFormation), automated deployments, automated recovery.

## Treat servers as disposable

Servers are **cattle, not pets**: if one misbehaves, **replace** it with a fresh copy from the AMI or template instead of nursing it back to health. This is only possible because everything is automated.

## How this shows up in questions

| The best answer usually… | Because of… |
|---|---|
| spreads resources across **multiple AZs** | design for failure |
| puts a **queue** between components | decoupling |
| uses **Auto Scaling** or serverless | elasticity |
| uses **CloudFormation** instead of manual steps | automation |
| uses a **managed service** instead of self-managed | less undifferentiated heavy lifting |

## Check yourself

1. What's a single point of failure, and how do you avoid one?
2. Which design principle does putting an SQS queue between two services follow?

### Answers

1. A component whose failure brings the whole system down (e.g. one server). Avoid it with redundancy: multiple instances across multiple AZs, plus load balancing and failover.
2. Decoupling (loosely coupled components).
