Day-to-day apps write lots of small transactions (OLTP: "place this order"). **Analytics** asks big questions across **huge amounts of historical data** (OLAP: "what were sales by region for the last five years?"). That needs a different kind of database: a **data warehouse**.

## Amazon Redshift

A **petabyte-scale data warehouse** for analytics and **business intelligence**.

- Built for complex queries across **massive historical data sets**.
- Stores data in **columns**, which makes "sum this one column over a billion rows" fast.
- Works with BI tools such as Amazon QuickSight for dashboards.
- **Redshift Serverless:** run analytics without managing clusters.

## OLTP vs OLAP

| | OLTP (transactions) | OLAP (analytics) |
|---|---|---|
| Typical query | "Insert this order", "get this customer" | "Total sales by region per month for 5 years" |
| Data | Current, many small reads/writes | Historical, huge scans |
| AWS answer | **RDS, Aurora, DynamoDB** | **Redshift** |

## Exam trap

Redshift is for **analytics, not transactions**. If the question describes an online shop's checkout, the answer is RDS/Aurora/DynamoDB, not Redshift. If it says "data warehouse", "business intelligence", "analyse historical data", it's Redshift.

## Where it fits

Redshift often sits at the end of a data pipeline (Module 8): data lands in S3, gets cleaned by AWS Glue, is loaded into Redshift, and is visualised in QuickSight.

## Check yourself

1. A company wants to run complex queries over 10 years of sales data for business reports. Which service?
2. Is Redshift a good choice for an e-commerce checkout system?

### Answers

1. Amazon Redshift (a data warehouse).
2. No: checkout is transactional (OLTP). Use RDS, Aurora or DynamoDB.
