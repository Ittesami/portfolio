**AWS Identity and Access Management (IAM)** controls **who** can sign in to your AWS account (authentication) and **what they're allowed to do** (authorisation). IAM is **global** (not tied to a Region) and **free**.

## The root user

Created when you open the account, using the sign-up email. It has **complete, unrestricted access**.

Best practice:

- **Turn on MFA** for it straight away.
- **Don't create access keys** for it.
- **Don't use it for everyday tasks.** Create an admin user (or use IAM Identity Center) and lock the root user away.

Only the root user can do a few things, such as **changing account settings or closing the account**, **changing the support plan**, and restoring IAM permissions if everyone is locked out.

## Identities

| Identity | What it is | Credentials |
|---|---|---|
| **IAM user** | A person or app with its own login | **Long-term** (password, access keys) |
| **IAM group** | A collection of users, e.g. "Developers", "Finance". Attach permissions **once** to the group | (none itself) |
| **IAM role** | An identity **assumed** temporarily by a user, an AWS service or an app | **Temporary** |

**New users have no permissions** until you give them some.

### Roles: the key best practice

When an EC2 instance or a Lambda function needs to use another service (e.g. read from S3), give it an **IAM role**. **Never store access keys on an instance.** Roles are also used for **cross-account access** and **federated users** (people signing in with a company identity).

## Policies

A **policy** is a **JSON document** that **allows** or **denies** actions on resources:

```json
{
  "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::my-bucket/*"
}
```

- Attach policies to users, groups or roles.
- **An explicit Deny always wins** over any Allow.

## Principle of least privilege

Grant **only the permissions needed** for the task, nothing more. If an answer option gives "AdministratorAccess" to fix a narrow problem, it's wrong.

## MFA (multi-factor authentication)

Password **plus** a second factor: an authenticator app code or a hardware security key. Turn it on for the root user and all human users.

## Single sign-on and app users

| Service | For |
|---|---|
| **IAM Identity Center** (successor to AWS SSO) | **Your workforce**: single sign-on across **multiple AWS accounts** and business apps; connects to an existing identity provider (e.g. Microsoft Entra ID / Active Directory) |
| **Amazon Cognito** | **Your app's customers**: sign-up and sign-in for web and mobile apps, including social logins (Google, Apple…) |

## Worked scenarios

> An application on EC2 needs to read files from S3. → Attach an **IAM role** to the instance.

> 20 developers need the same permissions. → Put them in an **IAM group** and attach the policy to the group.

> Employees should use their company login to access several AWS accounts. → **IAM Identity Center**.

## Check yourself

1. What's the safest way to let an EC2 instance access S3?
2. What should you do with the root user after creating the account?
3. A policy allows an action and another policy explicitly denies it. What happens?

### Answers

1. Attach an IAM role to the instance (no stored access keys).
2. Enable MFA, don't create access keys for it, and use a separate admin identity for everyday work.
3. It's denied: an explicit Deny always wins.
