When parts of an application talk to each other **directly**, one slow or failed part can bring down the rest. **Messaging** services sit in between so components are **decoupled**: they can fail, slow down or scale independently.

## Monolith vs microservices

- **Monolithic application:** all components are tightly coupled in one unit. If one part fails, it can take everything down.
- **Microservices:** small, **loosely coupled** services that talk through messages or APIs. One failing service doesn't cascade.

```
tightly coupled:   Orders ──→ Payments        (Payments down → Orders fail)
decoupled:         Orders ──→ [ queue ] ──→ Payments
                   (Payments down → messages wait safely in the queue)
```

## Amazon SQS (Simple Queue Service)

A **queue**. Producers send messages; messages **wait** in the queue until a consumer **pulls** (polls) them and processes them.

- Buffers work when consumers are slow or temporarily down: nothing is lost.
- Each message is processed by **one** consumer.
- Lets you scale producers and consumers separately.

Think: an order system drops each order into a queue; the payment workers take orders out at their own pace.

## Amazon SNS (Simple Notification Service)

**Publish/subscribe.** A message published to a **topic** is **pushed** to **every** subscriber at once: email, SMS, mobile push, Lambda functions, SQS queues, HTTP endpoints.

Think: one "order placed" message fans out to the email service, the analytics service and the warehouse at the same time.

## Amazon EventBridge

A **serverless event bus**. It receives events from AWS services, your own apps and SaaS apps, and **routes** them to targets based on **rules** (e.g. "when an EC2 instance stops, run this Lambda function").

## Telling them apart

| | SQS | SNS | EventBridge |
|---|---|---|---|
| Pattern | Queue | Publish/subscribe | Event bus with rules |
| Delivery | Consumers **pull** | **Pushed** to subscribers | Routed to targets by rules |
| Receivers | One consumer per message | **Many** (fan-out) | Whichever targets match |
| Keyword | "queue", "buffer", "decouple", "process later" | "notify", "fan-out", "send to multiple" | "events", "rules", "SaaS events", "react when…" |

Memory trick: **SQS = Queue** (pull, one at a time); **SNS = Notification** (push, to many).

## Worked scenario

> A web app must keep accepting orders even when the order-processing system is down for maintenance.

→ Put an **SQS queue** between them. Orders wait in the queue until processing comes back.

## Check yourself

1. Which service sends one message to many subscribers at once?
2. Which service lets messages wait until a consumer is ready to process them?
3. What's the main benefit of decoupling components?

### Answers

1. Amazon SNS.
2. Amazon SQS.
3. A failure or slowdown in one component doesn't bring down the others, and each part can scale independently.
